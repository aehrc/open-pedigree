## Why

The editor currently hardcodes its set of person fields (name, DOB, disorders, phenotypes, adopted, lost contact, etc.). Different implementers and deployments — especially SMART on FHIR launches, where the same editor instance serves multiple health services or research studies — want to capture different additional data per pedigree individual without a code fork. FHIR already has a standard mechanism for declaring and capturing arbitrary structured data: `Questionnaire` and `QuestionnaireResponse`. Adopting it lets an implementer configure extra fields by pointing at a FHIR resource instead of patching the editor's source.

## What Changes

- Add a `questionnaireUrl` (fetch from a FHIR server at startup) and `questionnaireLocal` (inline resource, no network fetch) option to `initialiseEditor()`.
- Support a flat-plus-groups subset of the FHIR Questionnaire item model: `item.type` of `string`, `text`, `boolean`, `date`, `integer`, `decimal`, `choice`/`open-choice` (via `answerValueSet`), and `group` for organisation. `item.enableWhen` (single-condition and multi-condition with `enableBehavior`) controls conditional visibility.
- Render configured items as additional fields in the node editor panel, grouped under a new "Custom" tab (alongside the existing Personal/Clinical/Disorders tabs).
- `choice`/`open-choice` items with `answerValueSet` integrate with the existing terminology subsystem (`src/script/terminology/`) to drive a searchable picker, reusing `FHIRTerminology`/`DelegatingTerminology` machinery rather than introducing a parallel terminology client.
- Each node's answers are held in memory as `questionnaireAnswers` (keyed by `linkId`) and persisted in the internal JSON serialisation, so answers round-trip through save/load same as any other node property.
- GA4GH FHIR export: for every node with at least one answered item, emit a contained `QuestionnaireResponse` resource — `subject` referencing the node's Patient (identical convention to `Condition`/`Observation`), `questionnaire` set to the configured Questionnaire's canonical URL (+ version), `item[]` mirroring the answered `linkId`s. Referenced from a new `Composition.section` (code `questionnaire-responses`).
- GA4GH FHIR import: read contained `QuestionnaireResponse` resources, resolve `subject` via the existing `resolveNodeRef` helper, and populate the matching node's `questionnaireAnswers`. If `QuestionnaireResponse.questionnaire` doesn't match the currently configured Questionnaire's canonical URL, log a warning and import the raw answers as opaque, non-rendered pass-through data (preserved on the node so a later re-export doesn't lose them, but not shown in the UI until the correct Questionnaire is configured).
- **Field mapping** — an item can optionally declare that its answer also feeds an *existing* FHIR representation, instead of only the generic `QuestionnaireResponse`:
  - `mapsToField`: the item's own `item.definition` (a core Questionnaire field, standard `<canonical-url>#<element-id>` syntax) names an existing converter-aware scalar node property — either a real Patient element (`gender`, name, identifier, birthDate, deceasedDateTime) or, for the four that don't correspond to one, this library's own self-hosted `PedigreeIndividual` logical model (`lifeStatus`, `gestationAge`, `carrierStatus`, `comments`). The mapped item writes/reads that property directly through its *existing* setter/getter and existing FHIR shape (`Patient.gender`, the fixed-code carrier-status `Observation`, etc.) — no new export/import code needed for this kind, since the existing converter code already serialises these properties. The item is not separately rendered on the Custom tab (it would duplicate a field the editor already shows elsewhere); the mapping only affects export/import.
  - `mapsToCondition` / `mapsToObservation`: the item's own `item.code` (a core Questionnaire field, `0..*` Coding) gives the code for a genuinely new fact with no existing hardcoded home. A `boolean` item mapped this way emits a `Condition` with that code when answered `true` (presence-based, like disorders); any other mapped type emits an `Observation` with `value[x]` set from the answer (always emitted when answered, like phenotypes). These items **do** still render on the Custom tab (there's no other UI for them). On import, generic disorder/phenotype extraction excludes any `Condition`/`Observation` whose code matches a configured mapping, so the fact isn't double-counted into both the generic list and the mapped item's answer. Derivation happens by walking the already-built `QuestionnaireResponse`'s own `item[]` (the same shape as FHIR SDC's `$extract` operation, implemented client-side rather than as a server operation), not by a separate scan of node properties.
  - Both kinds are **dual-write**: the mapped FHIR location is authoritative (read on import, and what most FHIR-aware consumers will see); the `QuestionnaireResponse` item is still emitted/read as a provenance record of what was asked and answered via the Questionnaire flow, but never overrides the mapped location if the two ever disagree.
- No changes to the existing hardcoded fields (name, disorders, phenotypes, etc.) — this is purely additive.

## Capabilities

### New Capabilities
- `questionnaire-fields`: Fetching/configuring a Questionnaire, rendering its items as node editor fields with `enableWhen` support, storing answers on nodes, and round-tripping them through GA4GH FHIR export/import as contained `QuestionnaireResponse` resources.

### Modified Capabilities
- `patient-provider`: No requirement changes. (The `answerValueSet` → terminology integration reuses the existing terminology subsystem, not the patient-provider subsystem; no `patient-provider` requirement is altered.)

## Impact

- **`src/pedigree.ts` / `initialiseEditor`**: new `questionnaireUrl` / `questionnaireLocal` options; fetch and parse the Questionnaire at startup.
- **New module** `src/script/questionnaire/` (or similar): Questionnaire model/parser, `enableWhen` evaluator, per-item-type field renderer, answer storage helpers.
- **Node menu / node editor panel** (`src/script/pedigree.ts` node-menu config, view layer): new "Custom" tab rendering configured items.
- **`src/script/terminology/`**: no interface changes; `answerValueSet`-backed choice items construct a `FHIRTerminology`/`DelegatingTerminology` instance the same way `disorderOptions`/`phenotypeOptions` do today.
- **`src/script/view/person.ts`** (or wherever node properties live): new `questionnaireResponseItems` property, serialised in `getProperties()`/`assignProperties()`.
- **`src/script/GA4GHFHIRConverter.ts`**: new `buildQuestionnaireResponse()`/`addQuestionnaireResponse()` (export) and `extractDataFromQuestionnaireResponse()` (import) following the existing `addConditions`/`addObservations`/`extractDataFromCondition` pattern; new `questionnaire-responses` Composition section; `deriveResourcesFromQuestionnaireResponse()` derives `mapsToCondition`/`mapsToObservation` resources by walking the already-built `QuestionnaireResponse`'s `item[]`, and `extractDataFromCondition`/`extractDataFromObservation` gain a code-exclusion check for mapped codes to avoid double-counting.
- **No changes** to PED/BOADICEA/GEDCOM/DADA2 import/export — those formats have no analogous extension point and simply won't carry questionnaire answers.
