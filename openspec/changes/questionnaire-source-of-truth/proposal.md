## Why

`questionnaire-fields` (shipped and archived) made the Questionnaire *additive*: it configures a separate "Custom" tab, while the Personal/Clinical tabs stay a static, hardcoded field-descriptor array in `PedigreeEditor.generateNodeMenu()` (`src/script/pedigree.ts`). That's fine for adding a handful of implementer-specific fields, but it means the Questionnaire is never a complete picture of the form, and an implementer who wants to reorganise, relabel, reorder, or omit *existing* fields has no way to do it short of forking the editor — exactly the problem `questionnaire-fields` set out to solve for new fields, still unsolved for the original ones.

Now that SMART on FHIR and `questionnaire-fields` are both stable, we want the Questionnaire to be the single source of truth for the *entire* node-edit form — Personal, Clinical, and Custom become one Questionnaire-driven form, not two mechanisms bolted together.

## What Changes

- `PedigreeEditor.generateNodeMenu()` stops being a static array. Node-menu tabs, field order, labels, and grouping are all derived from parsing a Questionnaire — the same one already configured via `questionnaireUrl`/`questionnaireLocal`. Tab names come from `group` item `text`, not hardcoded `'Personal'`/`'Clinical'`/`'Custom'` strings.
- **A built-in default Questionnaire** (`src/script/questionnaire/defaultQuestionnaire.ts`, a plain JS object shipped in source) is used whenever no `questionnaireUrl`/`questionnaireLocal` is supplied. It's functionally equivalent to today's hardcoded 21-field array (see Impact for the full inventory), so "no configuration" behaves exactly as it does today. There is always *a* Questionnaire — implementers who supply their own aren't required to replicate every existing field; unless stated otherwise items are additive to (not a replacement of) the built-in set (exact merge semantics are a design decision, see design.md).
- **Legend-backed repeating fields**: disorders, phenotypes, and candidate genes — currently `disease-picker`/`hpo-picker`/`gene-picker` NodeMenu field types backed by `DisorderLegend`/`PhenotypeLegend`/`GeneLegend` (a global, editor-level, cross-node colour-and-case-count tracker with its own floating UI, hover-to-highlight-on-canvas behaviour, and dynamic add/remove bookkeeping — `src/script/view/legend.ts`) — become Questionnaire items too, via a new mapping kind that says "this repeating choice item is legend-backed," reusing the generic `Legend` base class per-linkId instead of the three hardcoded subclasses.
- **A small, closed vocabulary of graph/app-state predicates**, usable from `enableWhen`-like conditions, covering exactly the non-FHIR-expressible visibility/availability rules already in `Person.getSummary()` today: `isFetus`, `hasRelationships` (once-alive), `isProband`, `isRelatedToProband`, `hasToBeAdopted`, `isTwinWithConsistentGender` / `isTwin`, `canLinkPatient`, `canImportClinicalData`. Critically, several of today's rules don't just show/hide a whole item — they disable *specific radio/select option values* within a still-visible item (gender options via `getPossibleGenders()`, life-status options via `hasRelationships()`, carrier-status options via current disorders/life-status). The predicate mechanism must support both whole-item show/hide *and* per-option disabling, plus the existing separate `inactive` (hidden) vs `disabled` (visible but greyed out) distinction (used today only by `monozygotic`). This is explicitly a bespoke, non-standard extension to `enableWhen` — nothing in the FHIR spec covers it.
- **Action items**: `link_patient` and `import_from_record` don't set a property at all — they open a modal via `editor.getPatientProvider()`. A new mapping kind marks a Questionnaire item as invoking one of a small, fixed set of built-in named actions (not arbitrary code), reusing the existing `button-action` NodeMenu field type and the existing action closures.
- The existing `mapsToField`/`mapsToCondition`/`mapsToObservation` mechanism, `item.definition`/`item.code` usage, and GA4GH FHIR export/import (`buildQuestionnaireResponse`/`deriveResourcesFromQuestionnaireResponse`) are unchanged in shape — the built-in default Questionnaire's scalar-property items use `mapsToField` exactly as any implementer-supplied Questionnaire would, reusing the already-correct setter-dispatch machinery (`Person`'s synthesized setters, `controller.ts`'s undo memo, the special-cased cross-field cascades for `setLifeStatus`/`setDeathDate`/`setDisorders`/`setCarrierStatus`) rather than reimplementing it.
- The docker-compose SMART demo environment's `tests/fixtures/smart/questionnaire.json` and `smartEditor.ts`'s wiring get updated to reflect the new default-Questionnaire-plus-implementer-additions model.

## Capabilities

### New Capabilities
- `questionnaire-source-of-truth`: the built-in default Questionnaire, whole-form generation from a Questionnaire (tabs/order/labels), legend-backed repeating items, the graph/app-state predicate vocabulary for `enableWhen`, and action items.

### Modified Capabilities
- `questionnaire-fields`: "Editor accepts a Questionnaire configuration" changes — there is always an effective Questionnaire (built-in default when none supplied), not "no Custom tab when neither option is given." "Supported Questionnaire item types render as Custom-tab fields" changes — there is no single hardcoded "Custom" tab; tab identity comes from the Questionnaire's own grouping. The `mapsToField` requirement changes — it no longer excludes the item from rendering (there is no longer a separate hardcoded field for it to duplicate); it renders normally like any other item, just dispatching through the existing real setter/getter instead of a generic per-linkId answer store, so the setter's own cross-field behaviour (undo cascades, etc.) keeps working. (Corrected during implementation — the original design draft carried the additive-model's exclusion requirement forward without accounting for the built-in default Questionnaire needing mapsToField items to actually render.)

## Impact

- **`src/script/pedigree.ts`**: `generateNodeMenu()` rewritten to build field descriptors and tabs entirely from the (default-or-configured) Questionnaire; the current 21-entry hardcoded array is deleted from here and re-expressed as the built-in default Questionnaire's items.
- **New**: `src/script/questionnaire/defaultQuestionnaire.ts` — the built-in default Questionnaire, covering every current field: `identifier` (hidden), `gender` (radio, `mapsToField`), `first_name`/`last_name` (text, `mapsToField`), `link_patient` (action item), `external_id` (text, `mapsToField`), `carrier` (radio, `mapsToField`), `evaluated` (checkbox), `disorders` (legend item), `import_from_record` (action item), `candidate_genes` (legend item), `hpo_positive` (legend item), `date_of_birth`/`date_of_death` (date, `mapsToField`), `state` (radio, `mapsToField`, life-status), `gestation_age` (integer/select, `mapsToField`), `childlessSelect` (choice), `adopted` (checkbox), `monozygotic` (checkbox), `nocontact` (checkbox, `mapsToField`), `placeholder` (checkbox — currently always inactive/hidden in the live UI; carried over as-is), `comments` (textarea, `mapsToField`).
- **`src/script/questionnaire/questionnaireParser.ts`**: new item-level extensions/parsing for legend items, action items, and predicate-based `enableWhen`/option-disabling; tab derivation from `group` items.
- **`src/script/questionnaire/enableWhenEvaluator.ts`** (or a new sibling module): the graph/app-state predicate vocabulary, requiring access to `editor.getGraph()`/`editor.getPatientProvider()` and the target node — a materially different input shape than today's pure item-answer evaluation.
- **`src/script/view/legend.ts`**: used directly (not subclassed) for arbitrary per-linkId legend instances; **`src/script/view/nodeMenu.ts`**: new `questionnaire-legend-picker` field type (generalising `disease-picker`/`hpo-picker`/`gene-picker`), extended `_setFieldInactive`/`_setFieldDisabled` to support per-option-value disabling driven by predicates for `radio`/`select` types (already partially supported — `inactive` as an array already means "disable these specific values" for `radio`, per existing code — the new work is *computing* that array from a predicate rather than bespoke `Person.getSummary()` logic).
- **`src/script/view/person.ts`**: `getSummary()`'s current bespoke graph-dependent computations (`inactiveGenders`, `cantChangeAdopted`, `inactiveMonozygotic`/`disableMonozygotic`, `inactiveCarriers`, `inactiveLostContact`, `inactiveStates`, `link_patient`/`import_from_record` capability checks) are re-expressed as predicate evaluations driven by the Questionnaire config, not hardcoded per-field logic.
- **`docker-compose.smart.yml` / `tests/fixtures/smart/questionnaire.json` / `src/smartEditor.ts`**: updated to the new model.
- **No change** to GA4GH FHIR export/import shape, `mapsToField`/`mapsToCondition`/`mapsToObservation` extension vocabulary, or the SDC `$extract`-shaped derivation — this change is about *what generates the form*, not how answers round-trip through FHIR.
